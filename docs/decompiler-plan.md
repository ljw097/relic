# 디컴파일러 설계

이 문서는 디컴파일러가 어떤 단계를 거치고 모듈이 어떻게 나뉘어 있는지 설명합니다. 처음에는 x86-64 하나로
계획을 세우고 만들었고, 그 계획(맨 아래 일정표)은 모두 끝났습니다. 지금은 x86/x86-64, ARM/Thumb, AArch64,
MIPS32/64, RISC-V RV32/RV64, PowerPC 32/64 리프터가 있습니다. GUI의 Pseudocode 탭은 백그라운드에서 디컴파일하고,
다른 함수로 옮기면 하던 것을 취소합니다. 남은 일(goto 줄이기, 구조체 값 전달, 속도)은 [TODO.md](../TODO.md)에
있습니다.

## 무엇을 노리나

- 분석 결과(`Analysis`, `Function`, `Block`, `Insn`)를 받아서 함수마다 읽기 쉬운 C 비슷한 의사 코드를 만든다.
- 포너블에서 필요한 정보를 먼저 챙긴다. 지역 버퍼 크기와 스택 오프셋, 호출 인자(특히 문자열 상수), 루프와
  분기 조건.
- 읽기 좋은 것보다 맞는 것이 먼저다. 복원하지 못한 부분은 감추지 않고 드러낸다(`__asm("...")`, `goto`).
- 출력을 다시 컴파일할 수 있게 만드는 것이 목표는 아니다. 하지만 테스트에서는 실제로 다시 컴파일해서 원본과
  같은 결과를 내는지 본다. 그게 가장 확실한 검증이라서다.

C++는 C로 씁니다. 분석 단계에서 RTTI로 클래스와 가상 호출 대상을 찾지만, 의사 코드는 메서드 호출 문법이 아니라
함수 호출로 나옵니다.

## 파이프라인

```
Function (blocks, insns)
  │ 1. lift           아키텍처별 리프터 → 블록마다 IR 문장
  ▼
IR CFG
  │ 2. ssa            지배자 트리, phi 삽입, 변수 버전
  │ 3. optimize       상수·복사 전파, 플래그 → 비교식, 죽은 코드 제거
  │ 4. calls/stack    호출 인자·반환값, 스택 슬롯 → 지역 변수
  │ 5. out-of-ssa     phi 제거, 변수 병합
  ▼
IR CFG (변수 단위)
  │ 6. structure      if/else, while/do-while/for, switch, break/continue, goto
  ▼
트리
  │ 7. types          폭, 포인터, 구조체, 라이브러리 원형
  │ 8. emit           C 텍스트와 줄 ↔ 주소 매핑
  ▼
의사 코드
```

`pipeline.prepare`가 1–6단계와 그 사이의 정리 패스를 차례로 돌리고(1–4단계 결과는 함수마다 캐시합니다),
`emit.decompile`이 타입을 마무리하고 C를 씁니다.

  lift/

`relic.analysis`는 디컴파일러 없이도 돌아야 합니다. 의존 방향은 `decompiler → analysis → disasm → loader`이고,
분석이 디컴파일러를 쓸 때(호출 인자, `assert()` 이름)는 함수 안에서 늦게 가져옵니다.

## 1. IR

작은 3-주소 형식입니다. 모든 값에 비트 폭이 있습니다.

- 값: `Const`, `Reg`, `Var`(SSA 변수), `Load`, `BinOp`, `UnOp`, `Cast`, `Extract`(상위 바이트 레지스터 같은
  부분 읽기), `Ite`(cmov), `Intrinsic`(parity, SIMD처럼 정밀하게 모델링하지 않는 연산), `Call`, `Phi`. 출력
  단계에서는 스택 슬롯을 뜻하는 `StackVar`, `StackAddr`가 더해집니다.
- 문장: `Assign`, `Store`, `Branch`, `Jump`, `IndirectJump`, `CallStmt`, `Return`, `Effect`(hlt, syscall),
  `Unknown`(리프팅하지 못한 명령, 출력은 `__asm`).
- 문장마다 원래 명령 주소가 붙어 있어서 GUI에서 리스팅과 오갈 수 있습니다.
- 플래그는 처음에 1비트 레지스터(`ZF`, `CF`, `SF`, `OF`, `PF`)로 리프팅합니다. 오버플로 플래그는 `sborrow` 같은
  연산자로 표현해 두어서, 나중에 `cmp a, b; jl`의 `SF != OF`를 `a <s b`로 접을 수 있습니다. 명령이 정의하지
  않는 플래그는 대입하지 않습니다.

## 2. 리프팅

- capstone의 상세 정보(피연산자, 레지스터 접근)를 씁니다. PowerPC는 capstone이 보여 주는 단순화된 니모닉이
  모호해서 명령 필드를 직접 해독합니다.
- 부분 레지스터 쓰기: x86-64에서 32비트 쓰기는 위 32비트를 0으로, 8/16비트 쓰기는 기존 값과 합칩니다.
- 지원하지 않는 명령은 `Unknown`으로 남기고 출력에 `__asm("...")`으로 보여 줍니다.
- 점프 테이블은 분석 결과(`Function.jump_tables`)를 `IndirectJump`의 후보로 씁니다.
- 아키텍처마다 다른 것(지연 슬롯, 조건 실행, 레지스터 쌍, TOC)은 리프터 안에서 끝내고, 그 뒤 단계에는 일반 IR만
  넘깁니다.

## 3. SSA와 최적화

- 지배자 트리는 Cooper–Harvey–Kennedy 반복 알고리즘으로 구합니다. 함수의 블록 수가 크지 않아서 이것으로 충분합니다.
- phi는 지배 경계에 넣고, 이름은 지배자 트리를 돌면서 붙입니다.
- 패스는 변화가 없을 때까지 반복합니다(`passes.optimize`). 상수 폴딩과 대수 단순화, 상수·복사 전파, load
  끌어오기, 조건식 복원, 죽은 코드 제거입니다.
- 전파는 SSA의 지배 성질에 기댑니다. load와 call이 없는 정의는 어디에나 대입하고, load가 든 정의는 한 번만 쓰이고
  같은 블록 안에서 메모리 장벽(Store, Call, Effect, Unknown)을 넘지 않을 때만 사용처로 끌어옵니다.
- 조건식 복원은 `cmp a, b`가 남긴 플래그 식(`SF = (a-b) <s 0`, `OF = sborrow(a, b)`, `ZF`, `CF`)을 알아보고
  `jcc`/`setcc`를 `a <s b`, `a <=u b` 같은 비교로 접습니다. `!`는 비교 안으로 밀어 넣어서 `!(a < b)`를
  `b <= a`로 씁니다.
- 상수 폴딩과 인터프리터는 같은 연산 함수(`apply_binop` 등)를 써서 의미가 어긋나지 않게 합니다.
- 검증: 인터프리터가 SSA를 그대로 실행할 수 있어서, 패스 전후의 함수를 같은 입력으로 돌려 결과와 메모리를
  비교합니다(`tests/test_passes.py`).

## 4. 호출과 스택

- 호출 규약은 `arch.py`의 표로만 접근합니다(SysV x64, Win64, cdecl, AAPCS/AAPCS64, o32/n64, RISC-V, PowerPC
  SysV/ELFv1/ELFv2). 리프터 다음 단계가 x86에 묶이지 않게 하려는 것입니다.
- import 함수는 시그니처 표와 원형(libc, Windows API, 사용자가 가져온 헤더)으로 인자 수를 정합니다. 포맷 문자열이
  있으면 거기서 셉니다. 내부 함수는 피호출자가 실제로 읽는 인자 레지스터로 정하고, 피호출자가 바꾸는 레지스터도
  호출 그래프로 계산합니다(`clobbers.py`).
- 스택은 진입 시점의 스택 포인터를 기준으로 오프셋을 정규화해서 슬롯을 만들고, 접근 크기와 주소를 넘기는 모양으로
  버퍼인지와 크기를 정합니다. 예를 들어 `lea rax, [rbp-0x50]`이 `gets`에 넘어가면 `char buf[...]`가 되고, 반환
  주소에서 얼마나 떨어져 있는지를 이름과 주석에 남깁니다. 포너블에서 가장 중요한 정보입니다.
- 카나리를 읽고 검사하는 코드(`fs:0x28`, `__stack_chk_fail`, AArch64 `__stack_chk_guard`, PowerPC 스레드 포인터)는
  출력에서 숨기고 함수 주석으로만 알립니다.

## 5. out-of-SSA와 정리

- phi마다 새 임시 변수를 만들어 각 선행 블록 끝에서 복사하고, phi 자리에서 그것을 읽습니다. 임시 변수는 phi 블록
  입구에서만 읽히니 critical edge를 쪼개거나 swap 문제를 따로 처리하지 않아도 맞습니다. 그다음 간섭 그래프로
  복사 관계인 변수를 합쳐서 복사를 없앱니다. 서로만 참조하는 phi 묶음(루프 안의 호출이 덮어쓰는 레지스터)은
  먼저 지웁니다.
- 반환값: 호출자의 IR에서 호출 직후 반환 레지스터를 어떻게 읽는지 봅니다. 아무도 안 읽으면 void, 모두
  `low32(rax)`로 읽으면 `int`입니다. 호출자가 없으면 함수 자신의 반환식으로 판단합니다.
- 폭 줄이기: 모든 사용처가 `low_n(v)`이거나 그대로 넘겨지는 변수는 n비트 변수가 됩니다.
- 임시 변수 인라인: 한 번 정의하고 한 번 쓰고, 같은 블록(또는 이어진 블록) 안이며, 그 사이에 메모리 쓰기, 호출,
  관련 변수 쓰기가 없을 때만 합니다. 호출 결과는 바로 다음 문장에만 넣습니다.
- 상수 나눗셈: 모양을 맞추는 대신 평가로 확인합니다. 변수 하나(`x`)로 된 식에 매직 곱셈이 있으면 몫, 나머지,
  나눗셈 판정 후보를 만들고, 경계값(0, ±1, 최솟값, 최댓값)과 난수 입력에서 원래 식과 모두 같을 때만 `x / c`,
  `x % c`, `x % c == r`로 바꿉니다.

## 6. 구조화

- 자연 루프(back edge)는 `while`/`do-while`, 유도 변수가 보이면 `for`가 됩니다.
- 조건 분기의 합류점(후지배자)으로 `if`/`if-else`를 만들고, 문장 없는 조건 사슬은 `&&`/`||`로 합칩니다.
- `IndirectJump`와 점프 테이블은 `switch`가 되고, 같은 값을 비교하는 if 사슬도 `switch`로 바꿉니다(`chains.py`).
- `break`/`continue`를 알아보고, 그래도 남는 간선은 레이블과 `goto`로 씁니다.
- goto를 줄이는 장치: 한쪽이 return이라 후지배자가 없는 if는 두 갈래가 모두 닿는 첫 블록을 합류점으로 삼고,
  이미 출력한 블록으로 다시 흐르면 작은 비순환 꼬리(6블록·12문장 이하)를 복제합니다. 예산을 키워 봤지만 줄 수만
  늘고 goto는 줄지 않았습니다(`/usr/bin/true`+`cat`에서 533 → 532 → 592).
- 남은 goto는 대부분 큰 상태 기계 함수에 있고, 이것은 조건 기반 구조화(DREAM 계열)로 풀어야 할 것 같습니다.

## 7–8. 타입과 출력

- 기본 타입은 폭으로 정하는 정수, 포인터, `char *`입니다. 사용처에서 제약을 모읍니다. 역참조하면 포인터,
  문자열 상수를 넣으면 `char *`, libc 원형의 인자면 그 타입, 비교의 부호(`jl`과 `jb`)로 signed와 unsigned를
  가릅니다.
- 구조체는 같은 기준 주소에서 고정 오프셋으로 접근하는 메모리를 모아서 만듭니다(`structs.py`). 전역에서 시작한
  구조체는 그 전역을 쓰는 모든 함수가 정의를 공유하므로, 한 함수를 디컴파일할 때도 관련 함수를 함께 살펴봐야
  합니다. 지금 디컴파일러가 느린 가장 큰 이유가 이것입니다.
- 이름 규칙: 매개변수 `a1`, 지역 변수 `v1`, 스택 슬롯 `var_c`, 버퍼 `buf_48`. 자동 이름(`varnames.py`)이 켜져
  있으면 쓰임새에 맞는 이름을 제안하고, 사용자가 붙인 이름이 항상 우선입니다.
- 출력 객체는 줄과 주소의 매핑을 갖고 있어서 GUI와 CLI에서 서로 오갈 수 있습니다.

## 검증

- 변환마다 IR 인터프리터로 전후를 비교합니다.
- 최종 C는 다시 컴파일해서 원본 소스와 같은 입력으로 돌려 결과를 비교합니다(`tests/test_emit.py`, 제어 흐름
  샘플 `tests/src/flow.c`는 `tests/test_flow.py`). 다른 아키텍처는 qemu-user로 돌립니다.
- 구조화는 무작위 CFG로 따로 검증합니다. 구조화한 트리를 실행하면 원래 CFG와 같은 순서로 블록을 밟는지
  (`tests/test_structure.py`), 출력한 C가 같은 순서로 도는지(`tests/test_emit_exec.py`) 봅니다.
- 실제 바이너리(`/usr/bin/{true,cat,ls,gzip,sed,grep}`)의 모든 함수에서 예외 없이 도는지도 확인했습니다.
- 재컴파일 비교에는 빈틈이 있습니다. 나중에 쓰이지 않는 값이면 두 변수를 잘못 합쳐도 결과가 같아서 테스트를
  통과합니다. 실제로 `arg_8`/`var_8` 이름 충돌이 이렇게 빠져나간 적이 있습니다. 그런 경우는 출력 모양을 확인하는
  회귀 테스트로 메웁니다.

## 처음 세운 일정

x86-64로 처음 만들 때의 계획입니다. 단계마다 `tests/src/vuln.c`로 골든 테스트를 붙였습니다. 출력 전체를
비교하지 않고 핵심 구문(호출, 조건, 루프 모양)이 들어 있는지만 봐서, 출력 형식을 바꿔도 덜 깨지게 했습니다.

| 단계 | 내용 | 완료 조건 |
|---|---|---|
| 1 | IR과 x86-64 리프터 | `vuln64.out`의 모든 함수가 `Unknown` 없이 리프팅됨 ✅ |
| 2 | SSA와 최적화 패스 | `checksum` 루프의 식이 `h = h * 31 + s[i]` 꼴로 접힘 ✅ |
| 3 | 호출과 스택 | `vuln`에서 `gets(buf)`, `char buf[0x40]`(PIE는 0x48), 카나리, `printf("hello %s (%d)\n", buf, checksum(buf))` ✅ |
| 4 | 구조화 | `main`의 `while (1)` 메뉴 루프와 `classify`의 `switch`가 goto 없이 나옴 ✅ |
| 5 | 타입과 출력 정리 | `-O0`, `-O1`, PIE 모두에서 위 결과가 유지되고, 다시 컴파일한 결과가 원본과 같음 ✅ |
| 6 | GUI 디컴파일 탭, x86-32 리프터 | GUI 스모크 테스트, x86-32 샘플 재컴파일 테스트 ✅ |

## 위험 요소

- **최적화된 코드(`-O2`).** 꼬리 호출, 레지스터 재사용, 조건부 이동 때문에 구조화가 어려워집니다. 그래서 처음에는
  `-O0`/`-O1`에 맞추고 `-O2`는 회귀 테스트로만 지켜봤습니다. 지금은 제어 흐름·부동소수점 샘플 같은 주요
  샘플을 `-O2`로도 다시 컴파일해서 비교합니다.
- **간접 호출과 점프.** 풀지 못하면 `goto`나 `(*ptr)(...)`로 남기고, 분석이 거기서 멈추지 않게 합니다.
- **성능.** 순수 Python이라 큰 함수에서 느립니다. 함수 단위로 필요할 때 디컴파일하고 결과를 캐시하며, 블록과
  명령 수에 상한을 둡니다.
