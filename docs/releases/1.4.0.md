# Relic 1.4.0

C++ virtual calls are now resolved on ARM, MIPS, RISC-V and PowerPC, not just x86 and
AArch64. The GUI gets a window for comparing two builds, and stripped programs for those
processors get their `main` found more often.

## New

**Virtual calls on ARM, MIPS, RISC-V and PowerPC.** Relic follows a C++ object from where it is
made (a constructor, a vtable stored in place, `dynamic_cast`, a function that returns it, an
argument) to the call through its vtable, and lists the methods that call can reach. This
covers ARM and Thumb, MIPS in both byte orders and MIPS64, RISC-V, and 32-bit and 64-bit
PowerPC (ELFv1 and ELFv2), at -O0 and -O2. The targets go into cross references and the call
graph, and argument recovery uses them.

**File > Compare with older build.** `relic diff` in the GUI. It lists the functions that
changed (most changed first), were added, were removed or stayed the same. Pick one to see
its diff in instructions or pseudocode, double-click to go to it, or port the older build's
names and comments with one button.

## Fixed

- **C++ classes on other processors.** On ARM, vtable entries kept the Thumb bit, so virtual
  methods got no names. Big-endian PowerPC64 (ELFv1) vtables point to function descriptors, so
  they were read only partway. On 32-bit PowerPC without PIC, libstdc++'s typeinfo vtables are
  copied into the program, and three of the five test classes were missed.
- **Big-endian PowerPC64 (ELFv1) glibc programs.** Their call stubs weren't recognised, so no
  imported function had a name, and a stripped program had no `main`.
- **`main` in static, stripped programs** when there are no signatures for that C library: MIPS
  (both byte orders), RISC-V, ARM, 32-bit PowerPC and PowerPC64 (ELFv1 and ELFv2) now find it.
- **`relic diff --port --overwrite`** counted comments that were already the same as ported.

## Faster

To find a callee's `long double` stack parameters, the decompiler looked into that callee's
callees too, which lifted most of the call graph for a single function. It now only looks at
functions that can take one (they use 80-bit values, or call one that does). The output is the
same; opening bash's `main` for the first time went from 34.8 to 27.8 seconds.
