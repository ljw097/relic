# Relic 0.3.0 (beta)

This release is mostly about auto-analysis, and I now consider that part done. Relic finds
functions even when there's no unwind info, rebuilds C++ classes from RTTI, and works out where
indirect and virtual calls go. It's also about five times faster on large binaries. Overall I'd
put it at about 88% of IDA Pro 9 + Hex-Rays, up from 83%.

Start it, then open a file with File > Open (`Ctrl+O`) or by dropping it on the window. The macOS
app isn't signed, so right-click it and choose Open the first time. There's also a wheel for
installing with pip (Python 3.10+).

## What's new

**Binaries without `.eh_frame`.** Relic now works out on its own which functions never return,
so their callers no longer run on into whatever comes next. It also recognizes tail calls and
finds functions that are only reachable through pointers stored in data. It also stopped
treating ordinary numbers as function pointers. I tested this on bash with its `.eh_frame`
stripped out: it finds 99.96% of the functions (up from 99.0%). Only one function still runs
into the next one, where there used to be 140.

**Speed.** On x86 it no longer asks capstone for operand details it doesn't need. Finding the
functions in bash went from 34 seconds to 7.

**Indirect calls.** When a call goes through a function-pointer variable, Relic now figures out
which functions the variable can hold. This works on every processor it supports (x86, ARM,
AArch64, MIPS, RISC-V and PowerPC). The targets show up as cross references and as a comment
in the listing (`; → print_and_abort`). If every possible target never returns, the call is
treated as never returning too.

**C++.** Classes, their bases and their vtables are rebuilt from RTTI, for both gcc/clang and
MSVC binaries, stripped or not. Virtual methods get names like `Dog::vfunc2`, and there's a new
`relic classes FILE` command that lists everything. Virtual calls are resolved by following the
object through registers and stack slots, on x86-64, x86 and AArch64, both at `-O0` and `-O2`.
The object's class can come from a constructor call, a vtable written in place, a
`dynamic_cast`, a function's return value or argument, or `this` inside a virtual method.

**Data inside code.** On x86, strings and tables that sit inside `.text` are shown as data
instead of being disassembled. A table of function pointers there is followed to find the
functions it lists.

## Known limits

- The decompiler doesn't handle x87 floating point or structs passed and returned by value.
- Virtual calls through objects are only followed on x86 and AArch64.
- The debugger needs `gdb` (plus `qemu-user` or wine for programs from other systems).
