# Relic 1.1.2

A faster release. Opening a large binary and decompiling a whole program take a quarter to
nearly half less time. The results are exactly the same as 1.1.1: the same functions, names,
cross references and pseudocode.

## Faster

| | 1.1.1 | 1.1.2 |
|---|---|---|
| Opening stripped `gdb` (the analysis) | 28.9 s | 21.3 s |
| `relic decompile --all` on `make` | 44.6 s | 29.4 s |
| `relic decompile --all` on a MinGW program | 27.0 s | 14.5 s |
| `relic decompile --all` on `find` | 28.9 s | 19.6 s |
| `relic decompile --all` on `ls` | 22.1 s | 16.7 s |

Decompiling one function in the GUI is about a fifth faster.

- **Finding functions that are only called indirectly** was the slowest part of opening a large
  stripped program. Each time it found one, it went back over every gap between functions it had
  already looked at. It now looks only where something could have changed.
- **Decompiling a whole program** (`relic decompile --all`, or `-o` to write a C file) prepared
  many functions twice: once to see which structs their callers and callees use, and again for
  their own pseudocode. Each is now prepared once.
- **The decompiler's own steps** do less repeated work: dominance between blocks, finding where
  the two sides of an `if` meet, removing stack writes nobody reads, and copying and walking the
  intermediate code.

## Fixed

- **`relic decompile --all` stopped with a Python traceback** on MinGW programs, at
  `__CTOR_LIST__`: a name on data inside the code, which has no instructions to decompile. That
  place now says so (`// __CTOR_LIST__ @ 0x14000ec10: not decompiled (...)`) and the listing goes
  on, as the C export already did. Asking for that function alone gives a one-line error.
