# Relic 1.1.2

This release is about speed. Opening a large binary and decompiling a whole program take
roughly a quarter to a half less time than in 1.1.1. The output hasn't changed: you get exactly
the same functions, names, cross references and pseudocode as before. I checked this against
more than a hundred binaries.

## Faster

| | 1.1.1 | 1.1.2 |
|---|---|---|
| Opening stripped `gdb` | 28.9 s | 21.3 s |
| `relic decompile --all` on `make` | 44.6 s | 29.4 s |
| `relic decompile --all` on a MinGW program | 27.0 s | 14.5 s |
| `relic decompile --all` on `find` | 28.9 s | 19.6 s |
| `relic decompile --all` on `ls` | 22.1 s | 16.7 s |

Decompiling a single function in the GUI is about 20% faster.

Most of the time spent opening a big stripped program goes into finding functions that are only
called indirectly. After each one it found, it used to go back over every gap between functions
it had already checked. Now it only looks where something could actually have changed.

Decompiling a whole program (`relic decompile --all`, or `-o` to write a C file) prepared a lot
of functions twice. It did each one once to see which structs its callers and callees use, then
again for its own pseudocode. Now each function is prepared once.

The decompiler's internals also do less repeated work in several places: dominance checks,
finding where the two branches of an `if` meet, removing unused stack writes, and copying and
walking the intermediate code.

## Fixed

**`relic decompile --all` stopped with a Python traceback on MinGW programs.** It got stuck on
`__CTOR_LIST__`, a symbol attached to data inside the code section, which has no instructions to
decompile. Now that spot gets a comment (`// __CTOR_LIST__ @ 0x14000ec10: not decompiled
(...)`) and the listing carries on, the way the C export already did. If you ask for that
function on its own, you get a one-line error.
