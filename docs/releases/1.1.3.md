# Relic 1.1.3

A bug-fix release for the pseudocode. Both bugs made C that looks fine but doesn't compile, or
compiles into something that reads the wrong memory.

## Download

| System | File |
|---|---|
| Windows (x86-64) | `relic-1.1.3-windows-x86_64.exe` |
| Linux (x86-64) | `relic-1.1.3-linux-x86_64.tar.gz`: one file, `relic` |
| macOS, Apple silicon | `relic-1.1.3-macos-arm64.zip`: `Relic.app` |
| macOS, Intel | `relic-1.1.3-macos-x86_64.zip`: `Relic.app` |

The macOS app isn't signed, so right-click it and choose Open the first time. The wheel is
attached too, for pip (Python 3.10+).

## Fixed

**The C export declared some structs twice.** When a function hands a struct to the functions it
calls, the struct picks up more fields as each of them is decompiled. `relic decompile -a -o
out.c` (and File > Export pseudocode) told declarations apart by their first line, which
includes the size, so the same struct could show up twice: a smaller copy first, then the full
one. A file like that doesn't compile. On `grep`, six structs were affected. Now each struct is
declared once, with every field it ended up with, in the place where it first appeared.

**Byte offsets from a variable's address were counted in the wrong units.** The pseudocode
could say `*(int *)((i * 12) + &table)` or `*(int64_t *)(&var_9c + 4)` (in tar's
`argp_parse`, for one). In C, adding to `&table` or `&var_9c` counts in multiples of the whole
object's size, not bytes, so compiling that reads somewhere else. These now come out as
`(char *)&table + i * 12` and `(char *)&var_9c + 4`.
