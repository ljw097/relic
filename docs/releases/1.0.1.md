# Relic 1.0.1

A bug-fix release. The debugger in the 1.0.0 Linux executable did not start, and `main` was not
found in some stripped programs.

## Download

| System | File |
|---|---|
| Windows (x86-64) | `relic-1.0.1-windows-x86_64.exe` |
| Linux (x86-64) | `relic-1.0.1-linux-x86_64.tar.gz`: one file, `relic` |
| macOS, Apple silicon | `relic-1.0.1-macos-arm64.zip`: `Relic.app` |
| macOS, Intel | `relic-1.0.1-macos-x86_64.zip`: `Relic.app` |

The macOS app is not signed: the first time, right-click it and choose Open. The wheel is also
attached, for installing with pip (Python 3.10+).

## Fixed

- **Debugger in the stand-alone executables: `error: gdb exited` right at start.**
  - The executable puts its bundled libraries on `LD_LIBRARY_PATH`, and gdb inherited it. On a
    newer system the Linux executable's older `libstdc++` stopped gdb from loading
    (`GLIBCXX_3.4.32 not found`).
  - gdb, qemu-user, wine and c++filt now start with the system's own library path, and so does
    the program being debugged.
  - If gdb does exit, the error now shows what gdb printed.
- **Start at `main` in a stripped program** ran it to the end without stopping, because gdb knows
  no `main` symbol there. It now stops at the `main` the analysis found, at its load address for
  a PIE.
- **`main` in stripped programs** is now found, so the program opens there instead of at the entry
  point, for:
  - 32-bit x86 PIEs, where `_start` passes it through a GOT slot.
  - Windows programs built with MinGW or MSVC: the call whose result the C runtime passes to
    `exit`. WinMain programs too.
- **Windows import thunks** (`jmp [__imp_exit]`) are named after their import (`exit`, `fwrite`,
  ...) and marked as library code. A thunk for a function that never returns, such as `exit`,
  now ends its callers' flow.
