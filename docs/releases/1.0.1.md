# Relic 1.0.1

A bug-fix release. The main one: the debugger didn't start in the 1.0.0 Linux executable on
newer systems. Also, `main` wasn't being found in some stripped programs.

## Download

| System | File |
|---|---|
| Windows (x86-64) | `relic-1.0.1-windows-x86_64.exe` |
| Linux (x86-64) | `relic-1.0.1-linux-x86_64.tar.gz`: one file, `relic` |
| macOS, Apple silicon | `relic-1.0.1-macos-arm64.zip`: `Relic.app` |
| macOS, Intel | `relic-1.0.1-macos-x86_64.zip`: `Relic.app` |

The macOS app isn't signed, so right-click it and choose Open the first time. The wheel is
attached too, for pip (Python 3.10+).

## Fixed

**The debugger failed with `error: gdb exited` as soon as it started.** The standalone
executable puts its bundled libraries on `LD_LIBRARY_PATH`, and gdb was inheriting that. On a
newer system, the older `libstdc++` bundled with the Linux build then kept gdb from loading
(`GLIBCXX_3.4.32 not found`). Now gdb, qemu-user, wine, c++filt and the program you're debugging
all start with the system's normal library path. If gdb does die, the error message now
includes what it printed.

**"Start at `main`" didn't stop in stripped programs.** gdb has no `main` symbol to break on
there, so the program just ran to the end. It now stops at the `main` the analysis found,
adjusted for the load address in a PIE.

**`main` wasn't found in some stripped programs**, so they opened at the entry point instead.
This affected 32-bit x86 PIEs, where `_start` passes `main` through a GOT slot, and Windows
programs built with MinGW or MSVC. For those, `main` is now the call whose result the C runtime
passes to `exit`. WinMain programs work too.

**Windows import thunks** like `jmp [__imp_exit]` are now named after the function they import
(`exit`, `fwrite`, ...) and marked as library code. If the import never returns (like `exit`),
the analysis now knows its callers stop there.
